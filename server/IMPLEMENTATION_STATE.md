## Manual KYC — implemented

The account flow is `/user/user/dashboard/verification`; admin review is `/admin/kyc`. Unverified users see a quiet prompt linking to the flow. The prompt changes for drafts, pending reviews and requests for changes, and disappears after approval.

1. Save legal name, date of birth, country of residence, residential address and document type.
2. Upload a passport photo page or identity document front, document back when required, and a face photo. Identity files accept PDF/JPG/PNG; face photos accept JPG/PNG. Maximum size is 3 MB per file.
3. Review and consent before submission. Required details and files are enforced by Laravel.
4. Submitted records are locked while pending. An admin can approve or request changes with a review note. Users can update and resubmit after a request for changes.
5. Approval updates the account's verification level. Notifications report submission and review outcomes.

Sensitive details, review notes and document contents are encrypted with Laravel's application key. Files are on the private disk and downloaded through authenticated owner/admin routes with no-store responses. Admin reads and decisions are audited. Version guards prevent an outdated review from overwriting a newer decision. Preserve the application key and private storage together with database backups.

Existing accounts with a positive verification level are treated as previously verified. That legacy flag does not establish that documents were reviewed in this new flow.

As of October 16, the admin queue searches names/emails and filters status on the server before pagination (25 records per page). Submission and review snapshots are encrypted, versioned and visible privately to the owner and admins; admin history reads are audited. Documents referenced by snapshots remain accessible after replacement. Existing submitted records were preserved as a labelled baseline during migration; files deleted before this update cannot be recovered. Draft files that were never retained in history are still removed when replaced. A version-checked **Request reverification** action requires a reason, removes verified status, records the decision and lets the user update and resubmit. History loads ten records at a time.

### KYC still outside this implementation

- Automated document authenticity checks, liveness, sanctions/PEP screening and ongoing monitoring.
- Product rules linking verification to deposit, withdrawal or investment limits. Approval currently changes verification status; it does not impose new money movement restrictions.
- Retention/deletion schedules and scheduled expiry-based reverification. Earlier documents deleted before history preservation was introduced are unavailable.

## Account settings, security and statements — October 16

Users have **Account settings** at `/user/user/dashboard/settings`; admins use `/admin/security`. Both support editing display name, phone and country, changing password, reviewing active sessions and signing out selected/other devices. Email and verified KYC identity details are not changed by profile edits. Password changes require the current password, enforce the existing length/complexity rules, invalidate password-recovery tokens and pending sign-in challenges, and revoke other sessions. Device details are browser-reported; legacy sessions may have no device metadata.

Authenticator enrollment uses RFC 4226/6238 SHA-1 TOTP with six digits and 30-second steps. Setup keys are encrypted, expire after ten minutes and are bound to the current session. QR codes are generated locally. A valid code confirms enrollment before it becomes active; ten random single-use recovery codes are shown once and stored only as hashes. Sign-in uses a hashed five-minute challenge with five attempts and issues no session before the second factor succeeds. Previously accepted time steps cannot be reused. Password changes, session revocation, disabling two-factor authentication and replacing recovery codes require the current password and a fresh factor when enabled. Security changes revoke other sessions. Password recovery does not disable two-factor authentication. Enrollment is available to users and admins and is recommended, but not mandatory, for admins; existing accounts were not enrolled automatically.

`/user/user/dashboard/statements` previews activity for an inclusive UTC date range of up to one year. CSV and printable HTML include all activity in that range (up to 50,000 rows per export), current USD/crypto balances and current investment records with their saved rates, terms, payout timing and paid profit. The screen previews the first 500 transactions; exports are not truncated to that preview. Manual deductions use their ledger direction. Current snapshots are explicitly distinguished from historical opening/closing balances; internal allocations are not represented as income. Exports are owner-scoped, no-store, escape spreadsheet formulas, and preserve exact crypto precision. PDF export uses the browser's print/save-as-PDF function.

`/admin/reconciliation` checks 25 accounts per page without changing balances. Checks cover USD investment/withdrawal reservations, crypto withdrawal/swap reservations, current balances against the latest ledger snapshots, and missing completed-swap ledger/receipt records. It is an internal consistency report, not an independent blockchain custody check or complete historical ledger reconstruction. The initial live check covered all six accounts and reported zero discrepancies; seven investments were retained and no swaps, funds or security enrollments were created by browser checks.

Users create a deposit instruction with its asset/network, receiving address and exact quantity. ### Crypto swaps — implemented October 16

Dashboard swaps use uninvested crypto only. A provider quote records source units, net destination units, included destination network fee, expiry and immutable treasury routes. Confirmation locks the user's account, consumes the quote once and reserves source units. Investing or withdrawing cannot reuse those units. Client retries preserve the original reference. Requesting or confirming a swap never opens a customer's wallet payment dialog.

The Changelly API v2 adapter signs exact JSON request bytes with RSA-SHA256. It checks runtime currency availability, asset/network mappings, token contracts and pair limits. Rate IDs expire after at most 50 seconds locally. `getFixRateForAmount.amountTo` is already net of the destination network fee; order creation checks `amountExpectedTo - networkFee`; settlement uses the authenticated transaction's actual `amountTo`. Provider order IDs are unique. Matching source amount, asset pair, payout/refund addresses, destination tags and payout hash are required before atomic source debit and destination credit. Distinct provider orders can share a batched payout hash; that hash cannot subsequently be submitted as a manual deposit. Existing USD investments and accrual terms are unchanged.

Order creation and treasury funding persist attempt markers before external calls. An uncertain creation is never blindly repeated: an admin can recover its provider ID and validate it through the provider API. Funding timeouts are reconciled through the existing transfer resource rather than another send. Hold, failure, mismatched settlement and unknown outcomes keep the source funds reserved. A proven unfunded expired order releases the reservation. For manual funding attempts, an admin may release an expired order only after verifying that no payment was sent; the provider must also confirm expiry with no received payment, and the action is audited. Provider refunds require a real refund hash and admin verification of the actual returned quantity, so fees/losses are not incorrectly refunded as a full amount.

#### Live setup

1. Obtain an approved Changelly Exchange API v2 account, registered API key and matching RSA private key (PEM, at least 2048 bits). Configure `CHANGELLY_API_KEY` and the absolute `CHANGELLY_PRIVATE_KEY_PATH` in the Laravel server environment. Keep the private key outside the web root and repository. API keys are never returned to the browser. Authentication and onboarding: https://docs.changelly.com/development/authentication and https://docs.changelly.com/.
2. Add actual platform-controlled receiving wallets in `/admin/settings`. Configure each swap asset's provider ticker and matching treasury wallet in **Crypto swaps** on that page. Only matching provider currencies are offered. Each source treasury address is also the refund address. Maintain sufficient treasury crypto and native network fees. Treasury sending fees are paid by the operator; the platform does not deduct another sending fee from the customer's quoted quantity.
3. Set `SWAPS_ENABLED=true` only after completing provider and treasury setup. Restart/reload the Laravel runtime configuration as appropriate. Without an automatic signer, use `/admin/swaps`: begin treasury funding before sending, send the exact amount to the provider address with its destination tag, then record the actual hash. Recording a hash never settles the user's balance by itself.
4. The existing scheduler runs `php artisan swaps:reconcile` every minute. This polls authenticated provider settlement records and the optional signer. It continues reconciling existing orders when new swaps are disabled. Provider-reported settlement is trusted; this is not an independent multi-chain node watcher.

#### Optional automatic treasury signer contract

Automatic swap funding requires a separately deployed, trusted signer/custody service; this repository does not contain a multi-chain private-key custodian. Set `SWAP_TREASURY_URL` to its HTTPS base URL and `SWAP_TREASURY_TOKEN` to its bearer token. Leave both empty for the implemented manual treasury workflow.

The adapter performs one `PUT /transfers/{swapId}` with `Idempotency-Key: {swapId}`. JSON fields are `idempotencyKey`, `assetKey`, `quantityAtomic` (exact integer string), `fromAddress`, `address`, nullable `destinationTag`, `expiresAt` (UTC), `provider` and `providerId`. The service must durably enforce one transfer per ID, exact source/network/token/amount/tag, fee and liquidity checks, and expiry before broadcast. Reusing an ID with changed parameters must fail. Subsequent uncertain-response recovery uses `GET /transfers/{swapId}`; a missing or unavailable result does not authorize resending.

Successful responses must echo `idempotencyKey`, `assetKey`, `quantityAtomic`, `address` and `destinationTag`, with `status: PENDING`, or `SUBMITTED`/`CONFIRMED` plus a network-valid `txHash`. `NOT_SENT` with no hash is permitted only as an irrevocable terminal guarantee that this ID never broadcast and can never broadcast later. That result prevents further send attempts and allows reservation release once the exchange order expires. Any ambiguous response retains the reservation for reconciliation. The signer must secure keys and outbound authorization itself; provider credentials alone cannot broadcast treasury funds.

At verification, live provider credentials were absent, swaps were disabled, and no receiving wallets or crypto balances existed. No exchange order or real crypto transfer was created by the tests.
